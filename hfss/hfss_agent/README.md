# hfss_agent：HFSS 自动设计 agent 的工具层

这就是之前说的"发动机"：大模型不写 PyAEDT 代码，只调用这里测试过的工具。

它原来是一个独立的项目，2026-11-08 复制进 Personal Agent，以后只在这里维护。桌面应用启动时自动拉起它（见上一级的 README），也可以像以前一样接给 Claude Code 等任何 MCP 客户端。

```
客户端 (Personal Agent 桌面应用 / Claude Code / 任何 MCP 客户端)
   ↓ MCP
server.py   接收请求，查参数，登记任务，马上返回 (不碰 AEDT)
   ↓ jobs.db
runner.py   后台排队：决定什么时候开新的 AEDT，处理取消、超时、内存不足
   ↓
worker.py   跑一个任务：调配方 → 启动 AEDT → 把结果写回 jobs.db
   ↓
recipes/    配方：给尺寸，出指标
```

- 每个任务都在数据目录的 `runs/<job_id>/` 里跑，**绝不打开你自己的 `.aedt`**。
- **数据目录**：`jobs.db`、`runs/`、`snapshots/` 和日志都放在环境变量 `HFSS_AGENT_DATA` 指的目录。桌面应用用 `%LOCALAPPDATA%\personal-agent\hfss`，因为结果可能有几十 GB，不能放进漫游配置；没设这个变量时用代码旁边的 `data/`。
- 任务记在 `jobs.db`，由后台进程执行，所以**关掉客户端，仿真也不会断**。
- 完全相同的请求不会重算，直接返回旧结果（`reused: true`）。模型或工程文件改过之后，旧结果自动失效。

## 两种用法

- **现成配方**（`submit_simulation`）：给尺寸就能自己建模。目前只有 `dr_filter`。
- **任意工程**（`inspect_project` + `run_project`）：你在 HFSS 里画好的任何带变量的模型，滤波器、天线都行。它负责改变量、仿真、取指标，但不能换结构。

## 工具

| 工具 | 作用 |
|---|---|
| `list_recipes` | 有哪些配方、参数的含义和范围、网格档位 |
| `submit_simulation` | 按配方提交仿真，立刻返回 `job_id` |
| `inspect_project` | 看任意工程里有什么：设计、变量、端口、边界、求解设置、扫频 |
| `run_project` | 改任意工程的变量并求解，立刻返回 `job_id` |
| `sweep_project` / `sweep_recipe` | 扫一个变量或参数：一次提交一组（最多 12 个点），返回 `sweep_id` |
| `compare_jobs` | 把几个任务或一次扫参放进一张表：改了什么、要点、网格、收敛、pitfalls |
| `get_job` | 查进度、取结果，`wait_seconds` 可以替你等；做完的结果带 `pitfalls`（踩坑检查，见 `pitfalls.py`） |
| `list_jobs` | 回顾算过什么（只给要点），也给进度：排第几、在做什么、跑了多久 |
| `cancel_job` | 取消任务，连同它的 AEDT 一起关掉 |
| `check_setup` | 环境自检：AEDT、许可证服务器、PyAEDT、数据目录空间、runner、本机核数内存（`doctor.py`） |
| `job_curves` | 给桌面应用画图：S 参数曲线、收敛过程、本征模表（`curves.py`）；应用不把它交给模型 |

## 任意工程怎么工作

工程要满足两点：尺寸和材料是**变量**，端口和边界已经设好。

- **原文件不动：** 提交时按内容存一份快照（`snapshots/`），任务只用快照的副本。排队时你改了原文件，也不影响已提交的任务。
- **求解设置：** 收敛判据按网格档位覆盖；工程原来的扫频全部换成一个插值扫频，默认用其中最宽的范围。
- **S 参数：** 任意端口数都给谷点、-10 dB 频段和端口阻抗；正好两个端口时再按滤波器算通带。
- **远场：** 工程有辐射边界就自动取，全向 5 度网格。默认只算 `f0_ghz` 一个频点，不多花时间；要看随频率的变化，用 `ff_sweep_ghz`，每个频点都要完整解一遍。
- **效率：** 辐射效率 = 增益 ÷ 方向性，总效率 = 实际增益 ÷ 方向性。AEDT 2025 R2 的 Antenna Parameters 报告用 pyaedt 取不到数据。
- **变量检查：** 名字写错、带单位的变量没写单位（不写会按米算），都会直接报错，不会开始仿真。

暂不支持：HFSS 3D Layout 和电路设计、多频点自适应、瞬态等其它求解类型。终端解（Terminal）、多模端口和三端口以上写了代码，但手头没有这样的工程，**还没用真实工程验证过**。

## 网格档位

| 档位 | 驱动模 ΔS | 本征模 Δf | 用途 |
|---|---|---|---|
| `coarse` | 0.02 | 0.2% | 扫参数、看趋势 |
| `fine` | 0.005（连续 2 次） | 0.05% | 写进文档、用来做决定的数字 |
| `verify` | 0.002（连续 2 次） | 0.02% | 在标称点复核 fine 的结果 |

每个结果都带 `converged` 和 `use`，说明这个数字能用来干什么。`converged` 不只看 HFSS 说收敛了没有，还会核对它实际用的判据是不是我们要求的那个。

## 并行

`runner.py` 的 `parallel_limits()` 按本机的物理核数和内存算，规则来自一台 i9-14900K / 48 GB 的实测，在那台机器上算出来正好是原来手调的值：

| | 规则 | 24 核 / 48 GB |
|---|---|---|
| 只有一个任务 | 物理核数，最多 16 | 16 核 |
| 多个任务时每个 | 物理核数的 1/3，最多 8 | 8 核 |
| 最多同时 | 3 个，且每个要约 16 GB 内存 | 3 个 |
| 已有任务时开新任务 | 空闲内存至少 16 GB 或总内存的 1/3 | 16 GB |

空闲内存掉到 1.5 GB 以下，会终止最晚开始的任务，防止机器卡死。实际用的值写在 `runner.log` 第一行。

## 本机参数

自动探测不对时，在数据目录里放一个 `settings.json`：

```json
{ "aedt_version": "2024.2", "max_jobs": 1, "cores_alone": 8, "cores_shared": 4, "min_free_gb": 12 }
```

- **AEDT 版本**：默认用装了的最新版，按安装程序设的 `ANSYSEM_ROOTxxx` 环境变量找，一个都没有就报错。
- **为什么不用环境变量**：runner 是经 WMI 启动的（这样关掉客户端也不会杀掉它），拿不到客户端的环境变量。数据目录本身通过命令行 `--data` 传给它。
- **HPC 许可证**：多于 4 核要 HPC 许可证。许可证不够时把 `cores_alone` 和 `cores_shared` 调小。

## 接到客户端

桌面应用会自动启动它。手动接给别的 MCP 客户端时，命令是 `.hfss\env\Scripts\python.exe -m hfss_agent.server`，工作目录是 `hfss`。

## 新增一种结构

先想想要不要加：只是调尺寸的话，在 HFSS 里画好模型、用 `run_project` 就够了。只有想让它**从零建模**时才需要写配方。

1. 仿照 `recipes/dr_filter.py` 写一个模块，提供 `NAME`、`DESCRIPTION`、`ANALYSES`、`PARAMS`、`CONSTRAINTS`、`prepare()`、`run()`。
2. 在 `recipes/__init__.py` 的 `RECIPES` 里加上它。
3. 用历史结果核对一遍数字，再交给大模型用。

## 测试

在项目根目录：

```bash
npm.cmd run test:hfss
```

在 `hfss` 目录：

```bash
..\.hfss\env\Scripts\python.exe -m hfss_agent.tests.smoke_client
```

```bash
..\.hfss\env\Scripts\python.exe -m hfss_agent.tests.smoke_project
```

第一个不需要 AEDT，几秒跑完，历史数据在 `tests/fixtures/`。后两个跑真实的 HFSS，各要几分钟。`smoke_project` 测远场要给天线工程的路径（不随仓库发布）。

改了 `runner.py` 之后，要等后台的 runner 空闲退出（约 2 分钟）才会生效。

## 验证记录（2026-11-01，`dr_filter` 默认几何）

| 档位 | f0 (MHz) | 插损 (dB) | 带宽 (MHz) | S11 谷底 (dB) | 加密次数 | 网格数 | 用时 |
|---|---|---|---|---|---|---|---|
| `coarse` | 3500.4 | 0.387 | 9.7 | −19.6 | 10 | 15.7k | 85 s |
| `fine` | 3500.2 | 0.392 | 9.5 | −24.6 | 13 | 45.7k | 327 s |
| `verify` | 3500.1 | 0.395 | 9.5 | −26.1 | 18 | 111.9k | 990 s |

- `coarse` 这一行和 `filter/dr_single/02_filter.py` 的结果完全一样。`fine` 和 `verify` 的 `f0_ghz` 用的是 3.504。
- 频率、插损、带宽到 `fine` 就稳定了。S11 谷底最敏感，`fine` 和 `verify` 之间还差 1.5 dB，所以回波指标要看 `verify`。
- 本征模：`coarse` 3.5088 GHz，`D=24.5` 时 3.4909 GHz，都和历史结果一样；`fine` 3.5044 GHz，`verify` 3.5039 GHz，和第 3 课的 3.504、3.5038 GHz 相差不到 0.5 MHz。
- 还测过：3 个任务并行、客户端中途退出后任务继续跑、取消、超时、内存保护、worker 报错。每次终止后 AEDT 进程都清干净了。

- 三个原工程的文件内容在测试前后完全一样（SHA-1 相同）。
